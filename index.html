Bottom line

Most of the stack is reasonable for a small, pre-revenue team. I would leave the web, mobile and BaaS choices alone for now. The part that needs attention is identity: a self-managed Postgres VM in Riyadh is tied to an EU Supabase database with application-level references. That creates both an outage risk and a data-residency risk.

The main issue

If the EU database stores a reference to identity data in KSA, you have two separate writes with a network hop between them. A failure during that hand-off can leave a booking or user record pointing at something that has not finished replicating. It also creates a path for identity-linked data to appear in EU logs, webhooks or caches.

Two execution paths

Booking and payment logic is split between Vercel functions and Supabase Edge Functions. Keep the business logic in one place; use Vercel mainly as the request layer.

Mobile identity releases

Expo OTA updates cannot replace a native Nafath SDK. Identity-related native changes will still need an app-store release.

Database connections

Direct 5432 connections from serverless functions can exhaust Postgres connections and show up as intermittent 500s.

No staging environment

The brief describes one Supabase project. A migration without a staging copy or rollback path is an avoidable release risk.

Identity stays in KSA

There is no application-level join from the EU database into the identity database.

One place to operate

OCI handles the connector, database, secrets and network path instead of a manually maintained VM.

Failures are contained

A container restart does not change the Nafath whitelist IP, and the database is not exposed with a public IP.

One practical rule

Do not try to solve all eight findings at once. Fix identity first, then harden secrets and networking, then clean up database connections and payment reconciliation.

Nafath connector
01Compute: Run the connector as an OCI Container Instance rather than maintaining a VM. It can restart automatically and scale to zero when idle.
02Database: Use OCI Database with PostgreSQL in Riyadh. Keep the database private and use managed backups / point-in-time recovery.
03Secrets: Put Nafath credentials in OCI Vault. The container reads them at runtime; nothing sensitive is stored in an env file on disk.
04Network: Put the connector in a private subnet and send Nafath traffic through an OCI NAT Gateway with a reserved public IP.
05Backups: Once a month, automatically restore a backup to a scratch instance. A backup that has never been restored is not a tested backup.
Recovery targets

Target an RPO measured in minutes through continuous WAL and an RTO of under one hour for a full regional failure. The restore should be an automated console action, not a manual DBA exercise.

Payments
One key per checkout: Use the same idempotency key for the payment attempt and the booking write so a retry cannot double-charge or double-book.
Verify webhooks: Check Moyasar and Tabby signatures before acting on webhook payloads. Keep the raw payload and verification result for reconciliation.
Explicit booking states: Use a real status flow: pending payment -> paid unconfirmed -> confirmed -> payout pending -> payout complete / failed.
Nightly reconciliation: Compare settlement exports with booking status. This is the one place where a person should need to look.
