What I would fix first

A practical review of the current web, mobile, payments and identity setup.

```

Bottom line

Most of the stack is reasonable for a small, pre-revenue team. I would leave the web, mobile and BaaS choices alone for now. The part that needs attention is identity: a self-managed Postgres VM in Riyadh is tied to an EU Supabase database with application-level references. That creates both an outage risk and a data-residency risk.
```

Next.js / Vercel, Expo / React Native, Supabase for platform data, and the existing payment providers are all workable at this stage. The goal should be to remove the failure modes that can block onboarding or create a compliance problem, not to redesign the whole stack.

01 · Current setup

Where the risk sits

The problem is not the number of services. It is the boundary between EU application data and KSA identity data.

```
CLIENTS Next.js / Vercel
Expo / React Native
SUPABASE (EU) Postgres · Auth · Storage
Edge Functions
MOYASAR / TABBY Cards · mada · Apple Pay
BNPL
cross-border reference
RIYADH VM Self-managed Postgres
Nafath connector · no HA
ELM NAFATH Government identity API
External
```
Current setup

Figure 1. Two Postgres databases are operated separately and linked by application-level references. The Riyadh VM is also a single point of failure for Nafath onboarding.

``` The main issue

If the EU database stores a reference to identity data in KSA, you have two separate writes with a network hop between them. A failure during that hand-off can leave a booking or user record pointing at something that has not finished replicating. It also creates a path for identity-linked data to appear in EU logs, webhooks or caches.

```
Other things to fix
```
Two execution paths

Booking and payment logic is split between Vercel functions and Supabase Edge Functions. Keep the business logic in one place; use Vercel mainly as the request layer.

Mobile identity releases

Expo OTA updates cannot replace a native Nafath SDK. Identity-related native changes will still need an app-store release.

Database connections

Direct 5432 connections from serverless functions can exhaust Postgres connections and show up as intermittent 500s.

No staging environment

The brief describes one Supabase project. A migration without a staging copy or rollback path is an avoidable release risk.

```

02 · Identity

A simpler boundary

The clean version is straightforward: Supabase gets a UUID; KSA keeps the actual identity record.

```
CLIENTS Next.js / Vercel
Expo / React Native
SUPABASE (EU) Platform data + UUID token
MOYASAR / TABBY Cards · mada · Apple Pay
UUID only ↓
OCI · RIYADH / JEDDAH · IN-KINGDOM
CONTAINER Nafath connector · scale-to-zero
POSTGRES HA + backups
VAULT Runtime secrets
NAT Static egress IP
ELM NAFATH Government identity API
```
Proposed setup

Figure 2. Supabase keeps only the opaque identifier. The KSA database is the only place that stores the National ID. The Nafath connector, database, secrets and outbound network path all stay inside one OCI tenancy.

Why this is better
```
Identity stays in KSA

There is no application-level join from the EU database into the identity database.

One place to operate

OCI handles the connector, database, secrets and network path instead of a manually maintained VM.

Failures are contained

A container restart does not change the Nafath whitelist IP, and the database is not exposed with a public IP.

```

03 · Findings

What matters, in order

The first two are blockers. The rest are important hardening work.

Level Area What can go wrong What to do
CRITICAL Identity database The Riyadh VM is a single Postgres node. A disk problem or kernel failure can stop Nafath verification and new-user onboarding. Move to OCI Database with PostgreSQL in Riyadh. Use managed backups and HA where available.
CRITICAL Identity data link EU and KSA Postgres are connected through application-level references. That creates race conditions and a risk that identity-linked data crosses the border. Replace the reference with a one-way UUID. Keep the National ID only in the KSA database.
HIGH Nafath credentials API credentials live on the VM filesystem. There is no clean rotation path and the VM becomes a valuable compromise target. Store credentials in OCI Vault and fetch them at runtime. Turn on automatic rotation.
HIGH Nafath outbound IP Scale-to-zero compute can change its outbound address. Government APIs commonly require a fixed allowlisted IP. Use an OCI NAT Gateway with a reserved public IP and allowlist that address.
HIGH Too many cloud vendors Adding another KSA cloud for the connector adds a second contract and another security boundary. Stay on OCI. Keep the identity path in one in-Kingdom tenancy.
MEDIUM Database connections Direct 5432 connections from serverless functions can exhaust the connection limit during normal traffic. Route application traffic through Supavisor in transaction mode.
MEDIUM Payment reconciliation A payment can succeed while the booking write fails, or the reverse. The system needs a way to find these mismatches. Use one idempotency key per checkout and reconcile against Moyasar / Tabby settlement data.
MEDIUM Vercel usage For photo-heavy listings, Edge Requests are likely to become a cost problem before raw bandwidth does. Serve listing images from zero-egress storage and alert before the included request quota is exhausted.
``` One practical rule

Do not try to solve all eight findings at once. Fix identity first, then harden secrets and networking, then clean up database connections and payment reconciliation.
```

04 · Implementation

How I would run the change

Keep the migration boring. The identity path is the part that deserves the most care.

```
Nafath connector
01 Compute

Run the connector as an OCI Container Instance rather than maintaining a VM. It can restart automatically and scale to zero when idle.

02 Database

Use OCI Database with PostgreSQL in Riyadh. Keep the database private and use managed backups / point-in-time recovery.

03 Secrets

Put Nafath credentials in OCI Vault. The container reads them at runtime; nothing sensitive is stored in an env file on disk.

04 Network

Put the connector in a private subnet and send Nafath traffic through an OCI NAT Gateway with a reserved public IP.

05 Backups

Once a month, automatically restore a backup to a scratch instance. A backup that has never been restored is not a tested backup.

Recovery targets

Target an RPO measured in minutes through continuous WAL and an RTO of under one hour for a full regional failure. The restore should be an automated console action, not a manual DBA exercise.

```
```
Payments
One key per checkout

Use the same idempotency key for the payment attempt and the booking write so a retry cannot double-charge or double-book.

Verify webhooks

Check Moyasar and Tabby signatures before acting on webhook payloads. Keep the raw payload and verification result for reconciliation.

Explicit booking states

Use a real status flow: pending payment -> paid unconfirmed -> confirmed -> payout pending -> payout complete / failed.

Nightly reconciliation

Compare settlement exports with booking status. This is the one place where a person should need to look.

```

05 · Monitoring & cost

What to watch

A short alert list, a separate cost watchlist, and a simple release checklist.

```

Alerts

These are the events that should wake an engineer.

Nafath Timeout or error rate stays above the agreed threshold.
Payments Moyasar / Tabby webhook failures stay above the agreed threshold.
Bookings Booking-to-payout success rate shows a sustained drop.
Database Postgres connections or CPU reach saturation.

Cost watch

These do not need paging. They need a dashboard and a monthly check.

Vercel Edge Requests

Photo-heavy listing pages can burn through request quota before bandwidth becomes the main issue.

Image delivery

Serve listing images from zero-egress storage instead of routing them through Vercel’s image pipeline.

Build execution

Watch CI build minutes; rebuilding on every push can quietly compound cost.

Tooling baseline

Sentry is enough for application exceptions. BetterStack or OCI monitoring can cover infrastructure uptime. The important part is the alert policy, not adding more monitoring products.

```
```
Dashboard only

CPU / memory — useful context, but not a page by itself.    Vercel usage — watch Edge Requests and Fast Data Transfer against the included quota.    Build minutes — look for CI jobs rebuilding unnecessarily.

```
``` BEFORE RELEASE
National ID exists only in the KSA database
Nafath credentials are not stored on disk
Outbound Nafath traffic uses one reserved IP
Backups have been restored successfully at least once
Payment / booking mismatches are reconciled automatically
Staging exists and migrations have a rollback path
```
